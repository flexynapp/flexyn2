# RLS Policy Coverage Audit — Flexyn migrations

Date: 2026-05-24. Scope: `supabase/migrations/*.sql`, with heavy focus on
130–146. Older tables (`user_profiles`, `hub_posts`, `hub_messages`,
`workout_logs`, etc.) audited previously; only flagged here when newer
migrations touched their policies.

Method:
- Grepped `CREATE TABLE public.<x>` across all migrations.
- For each newer table, verified `ENABLE ROW LEVEL SECURITY`, the set of
  `CREATE POLICY` clauses, and `GRANT ... ON public.<x>` to `authenticated`.
- Cross-referenced `src/` for `.from('<x>').<verb>(...)` to detect mismatches
  between policy/grant and the verbs the client actually uses.

Severities:
- **critical** — data leak, economy exploit, or universal client crash
- **high**     — entire user-facing flow silently broken by RLS
- **medium**   — flow partially broken or footgun
- **low**      — defense-in-depth gap

| severity | table | issue | suggested-fix |
|---|---|---|---|
| high | `gym_verification_queue` | `rejectVerification()` in `src/lib/data/gymBusinesses.js:77-87` issues a direct `UPDATE` to set `status='rejected'`. Mig 135 grants only `SELECT, INSERT` and creates only `read own` + `insert own` policies. The reject button is silently RLS-blocked. (Approve goes via `approve_gym_verification` SECURITY DEFINER RPC — fine.) | Wrap the reject in a `reject_gym_verification(p_id, p_reason)` SECURITY DEFINER RPC gated on `is_app_admin(auth.uid())`, mirroring `approve_gym_verification`. Remove the direct UPDATE from the client. |
| high | `gym_verification_queue` | `listPendingVerifications()` in `src/lib/data/gymBusinesses.js:59-67` runs `.select('*').eq('status','pending')` directly. Mig 135's only SELECT policy is `read own` (USING `owner_id = auth.uid()`). The admin queue returns 0 rows for everyone — admins can never see pending submissions. | Add a `list_pending_gym_verifications()` SECURITY DEFINER RPC gated on `is_app_admin`, returning the queue rows. Replace the direct select. |
| high | `cycle_logs` | `updateLog()` in `src/lib/data/cycleLogs.js:50-58` issues `.update(patch)`. Mig 128 has policies for SELECT / INSERT / DELETE only and grants `SELECT, INSERT, DELETE` — no UPDATE policy, no UPDATE grant. Editing a logged period silently fails. | Add `CREATE POLICY "cycle_logs: update own" FOR UPDATE USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid())` and `GRANT UPDATE ON public.cycle_logs TO authenticated`. |
| medium | `crew_message_reactions` | Mig 130 grants only `SELECT, INSERT, DELETE`; UPDATE policy intentionally absent. App uses RPC + occasional direct delete (`crewMessageReactions.js:14,56,65`). OK as-is — flagged only for future awareness. | None — `toggle_crew_reaction` covers writes. |
| medium | `marketplace_bundles` | Mig 134 has `bundles: seller manage` `FOR ALL` policy and grants `SELECT, INSERT, UPDATE` but NOT `DELETE`. A seller cancelling their bundle via a hypothetical direct delete would be blocked by missing GRANT despite the policy allowing it. | If the cancel flow ever issues a direct DELETE, add `DELETE` to the GRANT. Currently no `marketplace_bundles` delete call exists in `src/`, so risk is low. |
| medium | `monthly_leagues` | INSERT policy `WITH CHECK (true)` and UPDATE policy `USING (true)` — any authenticated user can INSERT arbitrary league rows and UPDATE any league row's `is_resolved`, `member_count`, etc. The legit writer is `record_monthly_xp` (SECURITY DEFINER, bypasses RLS anyway). | Tighten to service_role / postgres only: `CREATE POLICY ... FOR INSERT TO service_role WITH CHECK (true);` and drop the `authenticated` insert/update grants. The RPC keeps working since SECURITY DEFINER runs as `postgres`. |
| medium | `monthly_league_members` | `monthly_lm: write` policy is `FOR ALL TO authenticated USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)`. A user can self-INSERT into any league with arbitrary `monthly_xp`, bypassing the `record_monthly_xp` cap of 5000/call that mig 147 enforces. | Remove the `monthly_lm: write` policy and rely on `record_monthly_xp` (SECURITY DEFINER) for all writes. Or scope WITH CHECK to require `monthly_xp = 0` so init is harmless but increments must go through the RPC. |
| medium | `gym_events` | `gym_events: owner write` is `FOR ALL` USING `gym_businesses.owner_id = auth.uid()`. There's no INSERT-arm `WITH CHECK` — but combined with the separate `gym_events: member create` policy this is harmless. The redundant FOR-ALL means owner can also UPDATE/DELETE; no app code uses these (`gym_events.update` returns 0 matches in `src/`). | None functional. Consider splitting `FOR ALL` into explicit `FOR DELETE` + `FOR UPDATE` policies for clarity. |
| medium | `gym_businesses` | Mig 135 SELECT policy `USING (TRUE)` — authenticated users can read inactive gyms (including `phone`, `owner_id`). Mig 142's anon policy correctly filters `is_active = TRUE`, but the authenticated policy was never tightened. | Tighten to `USING (is_active = TRUE OR owner_id = auth.uid())` so an owner can still see their own deactivated gym. |
| medium | `gym_businesses` | No DELETE policy. If owners ever need to delete (vs `is_active = FALSE` soft-delete), the call will be RLS-blocked. Not currently called from `src/`. | Either add a `gym_businesses: owner delete` policy or document soft-delete-only and reject hard-delete attempts. |
| medium | `organization_members` | Mig 146 has no INSERT policy at all. Joining flows through `join_organization_by_code` SECURITY DEFINER RPC — correct. But there's also no UPDATE policy, so admins can't promote/demote a member via PostgREST. No update path exists in `src/lib/data/organizations.js` yet. | When the role-change UI lands, add a `promote_org_member(p_org_id, p_user_id, p_role)` SECURITY DEFINER RPC gated on `is_org_admin`. Don't add an UPDATE policy. |
| medium | `organizations` | No INSERT policy. Creation flows through `create_organization` SECURITY DEFINER RPC — correct. Direct insert by an authenticated user would be blocked, which is desired. | None — this is correct. Flagged for documentation. |
| medium | `gym_feed_posts` | No UPDATE policy. The `edited_at` column added in mig 138 suggests editing was planned, but no UPDATE policy was added and no UPDATE grant. Editing a feed post would silently fail. Currently no `gym_feed_posts.update` call in `src/`. | When edit lands, add `CREATE POLICY "gym_feed: author edit" FOR UPDATE USING (author_id = auth.uid()) WITH CHECK (author_id = auth.uid())` and grant `UPDATE`. |
| medium | `gym_feed_comments` | Same as above. `edited_at` column exists but no UPDATE policy / grant. | When edit lands, add author-only UPDATE policy + grant. |
| low | `bug_reports` (mig 007, status column added 144) | The new `status` column added in mig 144 is updated only via `resolve_bug_report` SECURITY DEFINER RPC. The original RLS for `bug_reports` predates this audit — but verify the original `FOR UPDATE` policy (if any) doesn't accidentally let users flip their own report's status to `dismissed`. | Read mig 007 RLS; if there's a self-UPDATE policy, narrow it so `status` is RPC-only (BEFORE-UPDATE trigger pattern from mig 142_user_profiles_privileged_columns). |
| low | `gym_event_rsvps` | Two separate policies for INSERT and UPDATE on own rows — fine, but the UPDATE policy has no `WITH CHECK`, only `USING`. A user could `UPDATE ... SET user_id = <other_user_id>` if not for the FK + UNIQUE constraint. Defense-in-depth gap. | Add `WITH CHECK (user_id = auth.uid())` to the `rsvp: own update` policy. |
| low | `gym_member_count` (denormalized counter on `gym_businesses`) | Updated only by trigger `trg_gym_members_count` — fine. But because the `gym_businesses: owner update` policy is wide-open on `FOR UPDATE`, an owner can UPDATE `member_count` directly to fake popularity. | Add a `gym_businesses_block_privileged_updates` trigger (mirroring mig 142_user_profiles_privileged_columns) that rejects direct writes to `member_count` from non-postgres callers. |
| low | `trainer_listings` | Auto-rollup counters (`sales_count`, `gross_cents`) are updated by the `trainer_listing_stats_sync` trigger but mig 143's `trainer update own` policy lets the trainer rewrite these directly via PostgREST. A trainer could inflate their own visible `sales_count` to fake credibility. | Add a BEFORE UPDATE trigger that rejects direct writes to `sales_count` / `gross_cents` from `current_user = 'authenticated'`. Same pattern as mig 142. |
| low | `monthly_leagues.member_count` | Same denormalized-counter exploit as above — any authenticated user can UPDATE `member_count` directly given the wide-open UPDATE policy. | Tighten the UPDATE policy per the medium finding above; the trigger pattern is unnecessary if writes are service_role-only. |
| low | `marketplace_bundles.seller_email` | Policy gates on `auth.uid() = seller_user_id` only. A seller could UPDATE `seller_email` to anything. The display surfaces this email, so a malicious seller could impersonate another user's email in the bundle card. Bounded — `seller_user_id` is still correct, so backend joins are safe — but UI may render wrong identity. | Add a trigger or column-level constraint that rejects writes to `seller_email` from non-postgres callers. | low | `gym_verification_queue` | INSERT policy `WITH CHECK (owner_id = auth.uid())` lets the client write arbitrary `business_name`, `proof_url`, etc. The `submit_gym_verification` SECURITY DEFINER RPC is the intended path — but the client could bypass it and stamp a verification with `status = 'approved'` directly via PostgREST since `status` is a regular column with the INSERT policy passing. | Add a `WITH CHECK (status = 'pending')` to the insert policy so the client can't pre-approve. Or remove the INSERT GRANT entirely and route ONLY through the RPC. |
| low | `journal_entries` | Owner-only RLS is correct. `attachments` is JSONB with no server-side cap; a malicious client could store unbounded JSON. Currently capped to 12 entries client-side (`journal.js:37`). | Add a `CHECK (jsonb_array_length(attachments) <= 20)` constraint for server-side enforcement. |
| low | `organization_challenges` | Insert policy correctly requires `is_org_admin(org_id) AND created_by = auth.uid()`. Delete policy correctly requires `is_org_admin(org_id)`. Good. | None. |
| low | `organizations.join_code` | No constraint forcing uniqueness check beyond the UNIQUE index; admin-update policy allows changing the join_code. A new join_code could collide with a soon-to-be-minted code in `create_organization` (12-retry loop). | Add a CHECK constraint format and document that admins shouldn't manually rewrite join codes. |
| low | `gym_events.created_by` | Mig 141 added a `creator delete` policy. But no `creator update` policy — an event creator can't edit their own event details (typo fix, time change). | When edit-event lands, add `CREATE POLICY "gym_events: creator update" FOR UPDATE USING (created_by = auth.uid()) WITH CHECK (created_by = auth.uid() AND gym_id = (SELECT gym_id FROM gym_events WHERE id = id))`. |
| low | `marketplace_listings` (mig 131 added `bundle_id`) | Mig 131 added `bundle_id` column but didn't add a policy that prevents a non-bundle-owner from setting `bundle_id` on listings they don't own. The existing seller-only UPDATE policy (mig 009) already gates on `seller_user_id`, so the attacker can only set `bundle_id` on their own listings — but they can attach their listings to ANY bundle, not just their own. ## Summary stats

- 7 new tables in 130–146 are fully clean (`crew_message_reactions`, `marketplace_bundles`, `gym_members`, `gym_feed_post_reactions`, `journal_entries`, `gym_feed_comments`, `gym_event_rsvps`).
- 3 user-facing flows are **silently RLS-blocked** today (gym admin reject, gym admin queue list, cycle log edit).
- 2 economy-relevant tables have wide-open UPDATE policies (`monthly_leagues`, `monthly_league_members`) that let any authenticated user bypass the rate caps enforced in `record_monthly_xp`.
- All newer tables have `ENABLE ROW LEVEL SECURITY` set — no "wide open" tables were found (the global ALTER DEFAULT PRIVILEGES from mig 085 ensures service_role grants come along automatically).
- The mig 142 `user_profiles_block_privileged_updates` BEFORE-UPDATE trigger pattern is the right model to extend to `trainer_listings.sales_count`, `gym_businesses.member_count`, `monthly_league_members.rank`, and `marketplace_bundles.seller_email`.
