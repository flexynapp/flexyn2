# Audit 10 — Hub user-visible behavior bugs

Date: 2026-05-25
Scope: Hub feed, Hub profile, Messages/DMs, Stories, Crews, Live activity,
Search, Follow suggestions. Looking specifically for things the user can
see — toggle desyncs, missing optimistic updates, broken nav targets,
counts that drift, mutes/blocks that don't actually hide, etc.

## Summary

The largest user-visible defects sit at the boundaries between optimistic
local state, server truth, and the per-user / per-device localStorage
layer.

The single highest-impact bug is in **HubMessages.jsx:144-152**:
`listFollowing()` returns an array of email STRINGS, but the consumer
maps it as if rows of `{ followee_email }` objects — so
`followingEmails` is permanently `[]`. Every DM partition decision
("inbox vs requests") then treats every conversation partner as a
non-followed stranger, and the entire "Requests" inbox concept is
effectively broken. Existing DMs from followed friends silently land
in "Requests" instead of "Inbox".

Second-largest: **LiveActivityRail.jsx:112** navigates to a route that
doesn't exist (`/hub/profile/${user_id}`). Tapping any "live now"
avatar lands on a blank page. The route the rest of the app uses is
`/hub?profile=<email>`.

Third-largest: **PostgreSQL polyglot of "live count" vs "stale count"**.
Reaction counts (HubPostCard `likeCount`, EmojiReactionButton, sticker
strip) compute display values from a mix of (a) the post's
denormalized counter, (b) optimistic adjustment for the current user's
own reaction, and (c) one-shot fetches that don't refetch on the post
window refresh. Three places drift in opposite directions; users notice
"I reacted but the count didn't change" or "the count is 7 but I see
8 stickers below the bar".

Several smaller issues compound: `@-mentions` in comments highlight but
aren't tappable; hashtags in post bodies only link when the post is
rendered from HubFeed; "muting" a conversation writes to localStorage
but doesn't suppress push or visually mute the row; pinned conversations
write to localStorage but never sort to the top of the inbox; story
reply auto-target relies on currentGroup.email which is correct, but
the toast "Open" CTA navigates to `/messages?conv=<id>` and Messages.jsx
doesn't pass that param into HubMessages — only HubMessages reads
`window.location.search` directly. Works by coincidence.
