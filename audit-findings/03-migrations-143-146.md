## 146_corporate_wellness.sql

| # | Severity | Line | Issue | Suggested fix |
|---|----------|------|-------|---------------|
| 1 | **critical** | 124 | `encode(gen_random_bytes(8), 'base32')` — Postgres's built-in `encode()` only supports `'base64'`, `'hex'`, `'escape'`. `'base32'` raises `ERROR: unrecognized encoding: "base32"`. Every call to `create_organization` will fail at runtime, meaning **no org can ever be created**. Same defect class as mig 101 (grant_flex_coins undefined) flagged in CLAUDE.md. | Use `'hex'` (and slice/translate to taste) or `'base64'`: e.g. `v_code := upper(substr(translate(encode(gen_random_bytes(6), 'base64'), '+/=Ol', '__-_0'), 1, 8));` or call `gen_random_uuid()::text` and slice. |
| 2 | high | 23 | `organizations.owner_id REFERENCES auth.users(id) ON DELETE CASCADE` — if the human who created the org deletes their account, the *entire org* (members, challenges, history) cascade-deletes. For a B2B portal that's almost certainly wrong (employee leaving ≠ company dissolving). | `ON DELETE SET NULL` plus an explicit transfer-ownership RPC; mark org as orphaned if `owner_id IS NULL`. |
| 3 | high | 201-205 | HR analytics: cohort floor `v_min_cohort = 3` only suppresses output when *total* `v_members < 3`. It does NOT suppress when an active sub-cohort is tiny — e.g. org of 50, `v_active_7d = 1` still exposes "1 person worked out". This violates the "can't single out one person" privacy pitch in the header comment. | Add `IF v_active_7d > 0 AND v_active_7d < v_min_cohort THEN v_active_7d := NULL; v_workouts_7d := NULL; END IF;` (and likewise round/redact `avg_workout_streak` when computed over <3 non-null streaks). |
| 4 | high | 48 | `organization_challenges.created_by REFERENCES auth.users(id) ON DELETE SET NULL`, but the INSERT policy `WITH CHECK (... AND created_by = auth.uid())` — if the creating admin's account is later deleted, `created_by` goes NULL. UPDATE policy `is_org_admin(org_id)` then still allows other admins to edit; OK. But the historical attribution is lost silently. Worth a paper-trail column. | Add `created_by_email TEXT` snapshot at insert (mirror the `reporter_email` pattern in `hub_reports`). |
| 5 | medium | 124 | Even if `base32` worked, the lowercase chars in the `translate` source string (`'oisb'`) are dead code: `encode(..., 'base64')` does emit lowercase, but `encode(..., 'base32')` (per spec) would emit uppercase + digits only. The whole sanitiser path is half-baked. | Pick one encoding and sanitise its actual character set. |
| 6 | medium | 126 | `IF v_try > 12 THEN RAISE EXCEPTION 'could not mint code';` — the raised exception has no ERRCODE; client gets a P0001 generic error. | `RAISE EXCEPTION 'CODE_MINT_FAILED' USING ERRCODE = 'P0001'` or return `jsonb_build_object('ok',false,'error','CODE_MINT_FAILED')` to match the rest of the function's contract. |
| 7 | medium | 110-138 | `create_organization(p_name)` — no length cap or content sanitisation on `p_name`. Client could submit 100KB of text. | `IF length(btrim(p_name)) > 80 THEN RETURN jsonb_build_object('ok', false, 'error', 'NAME_TOO_LONG'); END IF;` |
| 8 | medium | 87-92 | `organization_members: leave own` DELETE policy lets a member delete their own row — but if that member is the *sole admin*, the org is left adminless and no one can run analytics or admin RPCs. | Add a guard: refuse delete when role='admin' and they're the last admin. Implement via a BEFORE DELETE trigger or push the leave path through a SECURITY DEFINER RPC. |
| 9 | medium | 165-167 | `join_organization_by_code` returns `ok:true` whether the user newly joined or was already a member (ON CONFLICT DO NOTHING). The client can't distinguish "you're in" from "you were already in." | Use `INSERT ... ON CONFLICT DO NOTHING RETURNING id` and check FOUND; return `{ok:true, already_member:bool}`. |
| 10 | low | 30-36 | `organization_members` has no `updated_at`. Role changes (promote member→admin) won't be auditable. | Add `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` + trigger. |
| 11 | low | 40-50 | `organization_challenges` has no `updated_at`. | Add `updated_at` + a `BEFORE UPDATE` trigger. |
| 12 | low | 99-107 | No policy or RPC promotes a member to admin. Only seeded admin is the creator (via `create_organization`). | Add `set_org_member_role(p_org_id, p_user_id, p_role)` SECURITY DEFINER RPC gated by `is_org_admin(p_org_id)`. |
| 13 | low | 207-210 | `AVG(COALESCE(workout_streak, 0))` — averaging a streak that is NULL/0 for inactive members drags the avg toward zero, misleading admins. | Average over non-null only: `AVG(workout_streak) FILTER (WHERE workout_streak IS NOT NULL)` with a member-count denominator suppressed if `< v_min_cohort`. |
| 14 | low | 178 | `get_org_analytics` is `STABLE` and runs in `SECURITY DEFINER`. `STABLE` is fine but the function reads dynamic `now()` for the 7-day window — `STABLE` permits `now()` (which is stable within a tx). OK, but flag for awareness. | None — informational. |

## 145_journal_entries.sql

| # | Severity | Line | Issue | Suggested fix |
|---|----------|------|-------|---------------|
| 15 | medium | 18 | `user_email TEXT` is declared but NEVER populated — no DEFAULT, no trigger, and no client write is enforced. Will be NULL on every row. If the column is dead, drop it; if it's load-bearing for any downstream report, plumb it. | Either drop the column or add `DEFAULT (SELECT email FROM auth.users WHERE id = auth.uid())` (note: this only fires server-side on INSERT and only if column omitted), or set it via the INSERT policy WITH CHECK plus client convention. |
| 16 | medium | 24 | No `updated_at`-bumping trigger. Edits to title/body won't bump the timestamp, making "last edited" labels lie. | Add `CREATE TRIGGER trg_journal_updated BEFORE UPDATE ON public.journal_entries FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();` (assumes existing helper; otherwise create one). |
| 17 | medium | 22 | `attachments JSONB NOT NULL DEFAULT '[]'` — no CHECK constraint on shape or array length. A user could upload an array of 100k URLs and exhaust storage rows downstream. | Add `CHECK (jsonb_typeof(attachments) = 'array' AND jsonb_array_length(attachments) <= 20)`. |
| 18 | low | 17 | `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE` — fine, matches house pattern. Just confirm the deleteAccount RPC's table list (see `60_delete_account.sql`-style files) gets `journal_entries` added so manual deletes catch it before the cascade triggers fire. | Verify and add to the table list in the account-deletion RPC if it enumerates tables explicitly. |
| 19 | low | 19 | `entry_date DATE NOT NULL` — no CHECK preventing future dates (e.g. year 9999 typos) or pre-2020 dates. Minor. | `CHECK (entry_date BETWEEN DATE '2020-01-01' AND CURRENT_DATE + 1)` — the +1 covers timezone drift for last-minute entries. |
| 20 | low | 20-21 | `title` and `body` have no length caps. Possible abuse vector. | `CHECK (coalesce(length(title), 0) <= 200 AND coalesce(length(body), 0) <= 50000)`. |

## 143_trainer_tier.sql

| # | Severity | Line | Issue | Suggested fix |
|---|----------|------|-------|---------------|
| 27 | **critical** | 49 + 110-112 | Cascade-chain deadlock during account deletion: `trainer_listings.trainer_id REFERENCES user_profiles ON DELETE CASCADE`, but `trainer_purchases.listing_id REFERENCES trainer_listings ON DELETE RESTRICT`. If a trainer deletes their account, Postgres tries to CASCADE-delete their listings → which RESTRICT-fails because past purchases exist → the user_profile delete throws. **The trainer can never delete their account once anyone has bought from them.** | Change `trainer_listings.trainer_id` to `ON DELETE SET NULL` (and make the column nullable), OR change `trainer_purchases.listing_id` to `ON DELETE SET NULL`. Either way, also `SET NULL` on `trainer_purchases.trainer_id` to preserve buyer receipts when the trainer's profile is purged. |
| 28 | high | 110-112 | `trainer_purchases.trainer_id REFERENCES user_profiles ON DELETE CASCADE` — if the trainer's profile is deleted, every buyer's receipt is **cascade-deleted**, losing access proof and audit trail. This is also a privacy-violating data loss for the buyer. | `ON DELETE SET NULL` and add a denormalised `trainer_email_snapshot TEXT` for receipt continuity. |
| 29 | high | 204-211 | `get_my_trainer_revenue()` returns `SUM(amount_paid_cents)` etc. across ALL purchases including `is_mock = TRUE` rows. In dev/mock mode, real revenue numbers will be inflated by simulated checkouts that never charged a card. Trainer dashboard will display fake earnings as real money. | `WHERE trainer_id = auth.uid() AND is_mock = FALSE`, and add a separate `'mock_sales'` field if the studio dashboard wants to show test purchases distinctly. |
| 30 | high | 96-99 | `trainer_listings: trainer update own` UPDATE policy has no column restriction — a trainer can directly write `sales_count = 99999, gross_cents = 9999999` to inflate their own storefront stats since RLS allows full UPDATE on their rows. The rollup trigger only fires on `trainer_purchases` writes (server-side), so client-side tampering wins. | Either revoke client UPDATE on those columns via column-level GRANT (`GRANT UPDATE (title, description, price_cents, is_published) ON ...`), or move stats to a separate `trainer_listing_stats` table the client can't write. |
| 31 | medium | 89-94 | `trainer_listings: trainer insert own` INSERT policy subquery: `(SELECT is_trainer FROM public.user_profiles WHERE id = auth.uid())` — works because user_profiles has a public-read policy. But the subquery is evaluated per row; for bulk insert (unlikely here) it's wasteful. More important: there's no check that `is_published` is FALSE at insert (so an unverified user could publish on first insert if `is_trainer=TRUE`). | Either `WITH CHECK (is_published = FALSE)` on INSERT and require a separate publish RPC, or accept this and document. |
| 32 | medium | 113 | `trainer_purchases.regimen_id REFERENCES regimens(id) ON DELETE SET NULL` — if a trainer deletes their regimen, every buyer's purchase row loses the link to what they bought. The gated read policy (line 158-167) then never matches → buyers lose access silently. | Either RESTRICT the regimen delete when listings reference it, or snapshot the regimen JSON into `trainer_purchases.regimen_snapshot JSONB` at purchase time. |
| 33 | medium | 158-167 | `regimens: gated marketplace read` policy uses nested `IN (SELECT ... IN (SELECT ...))` — works, but each SELECT on regimens runs the subquery. EXISTS form is canonical and the planner sometimes prefers it. Functionally correct, performance-watch. | Rewrite as `EXISTS (SELECT 1 FROM trainer_listings tl JOIN trainer_purchases tp ON tp.listing_id = tl.id WHERE tl.regimen_id = regimens.id AND tp.user_id = auth.uid())`. |
| 34 | medium | 169-193 | `trainer_listing_stats_sync` trigger handles INSERT and DELETE but **not UPDATE**. If `amount_paid_cents` is ever corrected on an existing purchase row (refund adjustment, manual fix), `gross_cents` drifts. | Add `ELSIF TG_OP = 'UPDATE' THEN UPDATE ... SET gross_cents = gross_cents - OLD.amount_paid_cents + NEW.amount_paid_cents WHERE id = NEW.listing_id;` — and switch trigger to `AFTER INSERT OR UPDATE OR DELETE`. |
| 35 | medium | 196-211 | `get_my_trainer_revenue()` is `SECURITY DEFINER` but doesn't guard `auth.uid() IS NULL` — anonymous caller would see `{gross_cents:0, ...}` with `WHERE trainer_id = NULL` (no match). Not exploitable, but inconsistent with mig 146's pattern. | `IF auth.uid() IS NULL THEN RAISE EXCEPTION 'not authenticated' USING ERRCODE='42501'; END IF;` |
| 36 | medium | 70-75 | All five `DROP POLICY IF EXISTS` are correct, but `regimens: gated marketplace read` is dropped/created at lines 157-158 with no comment that the existing FOR ALL policy from mig 001 is still active. A future maintainer might accidentally drop/replace it. | Add a comment block: "DO NOT replace the regimens FOR ALL owner policy from mig 001 — RLS policies are OR'd". |
| 37 | low | 49 | `regimen_id UUID REFERENCES regimens(id) ON DELETE SET NULL` on `trainer_listings` — same concern as #32. | Same fix or snapshot. |
| 38 | low | 122 | `CHECK (amount_paid_cents = platform_fee_cents + trainer_payout_cents)` — good. But no CHECK that the split is roughly 15/85 — a misconfigured Edge Function could push 100% to platform or 100% to trainer. | Optional: `CHECK (platform_fee_cents BETWEEN amount_paid_cents * 10 / 100 AND amount_paid_cents * 25 / 100)` if the platform fee should always be ~15%. |
| 39 | low | 33-37 | `is_trainer BOOLEAN DEFAULT FALSE` plus `stripe_connect_id TEXT` added to `user_profiles` — the public-read RLS policy on user_profiles (mig 001 line 46-48 `using (true)`) means anyone can read another user's `stripe_connect_id`. While Stripe Connect IDs aren't secret, exposing them broadly is a privacy posture issue. | Move privileged trainer-payment columns into a separate `trainer_payment_profiles` table with owner-only RLS. |
| 40 | low | 64-67 | `trainer_listings_published_idx ON (is_published) WHERE is_published = TRUE` — partial index is fine, but storefront queries probably filter by `(is_published, created_at DESC)` or similar. Single-column index won't satisfy those efficiently. | Make it composite: `(created_at DESC) WHERE is_published = TRUE` for storefront sort, or `(price_cents, created_at DESC) WHERE is_published = TRUE`. |
