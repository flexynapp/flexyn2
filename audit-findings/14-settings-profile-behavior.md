# Audit 14 — Settings + Profile menu + Account management behavior

Scope: ProfileMenu.jsx, SettingsPanel.jsx, AvatarUploader.jsx,
TwoFactorSection.jsx, ConnectedAppsSection.jsx, ThemePicker.jsx,
LanguagePicker.jsx, ThemeContext.jsx, LanguageContext.jsx,
WeightUnitContext.jsx, SettingsContext.jsx, usePushSubscription.js,
adminRoles.js, dataExport.js, quietHours.js, notificationSnooze.js,
storyPrivacy.js, userBlocks.js, userMutes.js, _invokeDeleteAccount in
api/db.js, and the in-line bio/city/website editor in HubProfile.jsx.

Severity: **H**igh (user-blocking / wrong outcome / privacy or data
loss), **M**edium (degraded UX / surprising behavior), **L**ow (polish
/ edge case).

| 1   | H   | SettingsPanel.jsx (whole file)                     | No UI to change **weight unit** anywhere in Settings. `WeightUnitContext` exposes `setWeightUnit('lbs'|'kg'|'stone')` and is consumed by `LogWeightModal`, `BodyMetricsTab`, `GoalForm` via `UnitPill`, plus Onboarding's initial pick — but a user who chose lbs at signup and now wants kg has no path. Settings shows the distance unit toggle (mi/km) right next to it; the asymmetry will read as broken. The user can change unit *inside* a "log weight" modal via UnitPill but only if they happen to open one. Add a `lbs/kg/stone` segmented control next to the existing distance unit toggle. |
| 2   | H   | SettingsPanel.jsx (whole file)                     | No UI to **change email or password**. Grepping the entire `src/` directory for `resetPasswordForEmail`, `updateUser(...password`, `email_change` yields zero matches. A user who wants to rotate their password — or who finds out their account email is compromised — has no in-app affordance. Sole recourse is "forgot password" via the login screen. For an app that holds health data this is a glaring gap. |
| 3   | H   | ProfileMenu.jsx (lines 155-162) `handleSignOut`    | Race: `await db.auth.logout('/')` (api/db.js:312-317) sets `window.location.href = '/'` to redirect, AND THEN `wipeLocalClientState({ preserveKeys: true })` runs. The browser may begin unloading before the wipe iterates `localStorage.length` (~70 keys). On a fast network the unload wins, the wipe never completes, and per-device-scoped keys like `flexyn.celebratedCrewWars.<userId>`, `flexyn.pushOptInDismissed.<userId>`, `flexyn.iosInstallDismissed.<userId>` stay on the device after sign-out. A second user signing in on the same device inherits the first user's UX-state flags. Move the wipe BEFORE the logout (the comment claims order was reversed for Supabase token-revoke reasons, but Supabase keeps its own refresh-token in its own storage key — wiping localStorage AFTER signOut() has acquired the session object is safe). |
| 4   | H   | SettingsPanel.jsx (lines 297-311) `handleBlockAdd` (story blocks) | The block-list "Email to block…" input accepts any string with no validation that (a) the email is well-formed, (b) the email belongs to an actual Flexyn user, (c) it isn't the user's OWN email. A user can block "asdf@asdf", or themselves, or paste their attacker's email with a typo and never actually block them. `blockUser` in `lib/data/storyPrivacy.js:18-27` upserts blindly. Validate format + reject `email === user.email` + (ideally) verify the user exists before claiming success. |
| 5   | H   | SettingsPanel.jsx (lines 1067-1077)                | `{isAppAdmin(user) && <Link to="/admin/reports" …>}` — `isAppAdmin` (lib/adminRoles.js:18-23) is a **hard-coded client-side username allowlist** `['sean', 'seanj', 'kegan', 'admin']` plus an email-prefix check. Migration 084's `is_app_admin()` is the server-side source of truth (CLAUDE.md mentions it as the mirror). The link only controls visibility; the page itself must gate via server policy. But: (a) the comment in adminRoles.js says "Mirror of the username list in migration 084's is_app_admin() — when one changes, change the other," which is a maintenance footgun (drift between the two has already happened in this repo per the parallel-sessions warning), and (b) the email-prefix fallback means anyone who signs up with email `sean@anything.com` gets the admin chip rendered. Replace with a server-driven `is_app_admin` lookup at app boot. |
| 6   | H   | api/db.js (lines 482-705) `_invokeDeleteAccount`   | The "server-side" delete is actually **client-side**: it issues 50+ supabase deletes from the browser, then ALSO clears denormalized counters via `updateMe`. If RLS rejects any of these (e.g. `42501`) the row stays. The function reports `partial: true` to the caller, but `wipeLocalClientState` and `setAccountDeleted(true)` still run in ProfileMenu only on the success branch — yet the deletion is across 50 supabase round-trips and any one timeout will partial-fail. For a true server-side delete, this needs to be an Edge Function with `service_role` access. Until then it is racing against network conditions and any newly-added RLS-protected user-owned table. |
| 7   | H   | api/db.js _invokeDeleteAccount (lines 508-555)     | The deletion table list is hand-maintained. The comment ("EVERY new table added since this function was first written MUST be added here too — the audit found multiple tables…leaving orphan rows containing user-identifying data") admits the problem. As of mig 146 the list covers the known tables, but the moment migration 148+ adds another user-owned table this becomes a privacy bug again — the orphan row keeps PII after delete. The auto-fix is a server-side `delete_account_data()` SQL function that iterates `pg_catalog` for any column named `user_id` / `created_by` / `<role>_email` in `public.*` and deletes by it. Migration TODO. |
| 8   | H   | api/db.js _invokeDeleteAccount (line 621)          | `SCHEMA_SKEW_CODES` swallows `42703` (column not found) silently — comment claims this is "schema mismatch" tolerable as no-op. BUT 42703 from a `DELETE` does **not** mean "the user has no rows here" — it means the operation was malformed. The query never ran, and if the column WAS supposed to exist (a real migration drift), user rows persist undeleted with the user thinking deletion succeeded. Swallowing 42703 silently is a privacy hole disguised as resilience. Should at minimum emit a Sentry event so devs see when this fires. |
| 9   | H   | SettingsPanel.jsx (lines 388-405) `handlePrefToggle` | Optimistic per-category notification toggle calls `update_notification_pref` RPC. | 10  | M   | SettingsPanel.jsx (lines 260-272) `togglePrivacy`  | Direct `supabase.from('user_profiles').update({...}).eq('id', user.id)` for `is_private` / `hide_from_search`. | 17  | M   | SettingsPanel.jsx (lines 723-766) Quiet hours      | The two `<select>` dropdowns have IDENTICAL screen-reader labels in some locales ("Quiet hours start" / "Quiet hours end") but the visible label is just "Quiet hours" — a screen reader user opens the first dropdown, hears "Quiet hours start, 22, list, 24 options," picks one, hits next, "Quiet hours end" — they have no audible signal that this is a 24-hour clock. | 19  | M   | ProfileMenu.jsx (line 75-90) cookie sweep          | The cookie wipe uses `host.split('.').slice(-2).join('.')` to derive an apex domain.
