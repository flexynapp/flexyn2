## Findings

### F1 — CRITICAL: the capped XP path can be bypassed entirely

`authenticated` holds **column-level `UPDATE` on `total_xp`, `current_level`
and `flex_coins`**. The RLS policy on `user_profiles` is
`auth.uid() = id` — with no column list, because **RLS restricts which row,
never which column**.

Any signed-in user, with the publishable anon key and their own JWT, can:

```
PATCH /rest/v1/user_profiles?id=eq.<their own id>
{ "total_xp": 999999999, "flex_coins": 999999999, "current_level": 100 }
```

That bypasses, in one request:

- the per-action daily caps in `grant_action_xp` (mig 198)
- the 50,000/24h global cap in `increment_user_xp`
- the `xp_grant_log` audit trail
- the entire coin-economy hardening from migrations 197–207

**Evidence it is already happening.** Comparing `xp_grant_log` against
profiles:

| user | `total_xp` | XP in grant log | calls |
|---|---|---|---|
| sean | **559** | **0** | 0 |
| evrock | **100** | **0** | 0 |
| mrpeepee | **12** | **0** | 0 |
| seantest | **9** | **0** | 0 |
| gabe | 65 | 65 | 1 |
| kegan | 52 | 52 | 12 |
| kbfresh0711zzq | 51 | 51 | 9 |
| testrunner | 13 | 13 | 3 |

Four of eight ranked users have XP that never passed through the capped RPC.
Whatever wrote it, the door it used is open to everyone.

No client code writes these columns — I grepped every `updateMe` call site.
Server functions run as `service_role` or SECURITY DEFINER and are unaffected
by the `authenticated` grant. **Nothing legitimate needs it.**

### F2 — CRITICAL: the server computes levels with the old, broken curve

`increment_user_xp` still carries the pre-rebalance curve:

```sql
v_xp_needed := FLOOR(250 * POWER(v_mult, i - 1));
-- 1.10 / 1.13 / 1.16 / 1.20 by band
```

That is base **250** with per-band multipliers re-based from level 1 — the
exact discontinuity the client curve was rebalanced to remove. The client now
uses base 100 with continuous compounding at 1.110 / 1.085 / 1.050 / 1.040 /
1.030.

The two disagree, and the gap widens the whole way up:

| total XP | UI shows | `current_level` column | gap |
|---|---|---|---|
| 559 | Lv 5 | Lv 3 | +2 |
| 2,500 | Lv 13 | Lv 8 | +5 |
| 24,000 | Lv 36 | Lv 22 | +14 |
| 120,000 | Lv 62 | Lv 33 | **+29** |

`current_level` is not cosmetic — it is read by `GymRivalMenu`,
`GymRivalCard`, `CreateDuelModal`, `HeroSlideshow` and `ThemeSelector`. So a
user's level in the header and their level on a duel card are computed by two
different formulas and will visibly disagree.

It also feeds `grant_level_up_rewards`, so **rewards are paid against the old
curve while the UI celebrates the new one**.

### F3 — HIGH: `DAILY_XP_CAP` is dead code that contradicts the server

`DAILY_XP_CAP = 2500` in `xpSystem.js` is referenced by exactly one thing: its
own test asserting it equals 2500. Nothing enforces it.

The server's real ceilings are different by an order of magnitude:

| | Value |
|---|---|
| Client constant (unenforced) | 2,500 |
| Sum of per-action caps (mig 198) | ~5,029 |
| Global ceiling (`increment_user_xp`) | **50,000** |

So the documented policy is 2,500/day and the enforced policy is up to
50,000/day. At 50,000/day a user reaches **level 47 on day one** and level 66
by day three on the new curve.

### F4 — MEDIUM: cardio has no per-action cap

`grant_action_xp` classifies seven action types. The client sends **eight** —
`cardio_completed` is not in the `CASE`, so it falls to `ELSE NULL` and is
subject only to the 50,000 global ceiling. Workouts are capped at 4,000/day;
cardio is capped at 50,000/day.

### F5 — PRODUCT CALL: the new curve roughly doubles early-game payouts

Not a defect — the curve change was deliberate and correct — but the reward
schedule in migration 070 (per level ≥2: 1 standard + 50 coins; every 5th: +1
premium +100 coins; every 10th: +1 elite) was never re-checked against it.

| Path | XP | New Lv | Old Lv | Standard | Premium | Elite | Coins | Capsule value at shop prices |
|---|---|---|---|---|---|---|---|---|
| Day 1 @800 | 800 | 7 | 3 | 6 | 1 | 0 | 400 | 950 |
| Day 1 at cap | 2,500 | 13 | 8 | 12 | 2 | 1 | 800 | 2,900 |
| Week 1 @800 | 5,600 | 20 | 12 | 19 | 4 | 2 | 1,350 | 5,300 |
| Month 1 @800 | 24,000 | 36 | 22 | 35 | 7 | 3 | 2,450 | **8,950** |
| 6 months @800 | 144,000 | 65 | 33 | 64 | 13 | 6 | 4,500 | 16,950 |

A single hard workout (700 XP) takes a new user from level 1 to **level 6**,
paying 5 standard capsules and 250 coins in one save. One month of ordinary
training yields ~8,950 coins of capsule value — against a shop where the most
expensive item costs 1,000.

Whether that's excellent onboarding or a broken faucet is your call. Worth
noting the Silver tier starts at level 11 and Gold at 21, so **week one now
reaches Gold** — the ten cosmetic tiers in `xpTier.js` were paced for months.

## Stage 2 — What the references do differently

| Repo | Licence | Lesson |
|---|---|---|
| [`heroiclabs/nakama`](https://github.com/heroiclabs/nakama) | Apache-2.0 | The wallet is **only** mutable through `UpdateWallets`, which writes a ledger row per change. There is no table grant that lets a client touch a balance. Our `xp_grant_log` is the same idea — but ours is advisory, because the column is still directly writable (F1). |
| [`runelite/runelite`](https://github.com/runelite/runelite) | BSD-2 | `Experience.java` builds the XP table **once in a static block** and every lookup is an array index. Ours re-derives the curve in PL/pgSQL on every single grant — and that duplicated derivation is exactly what drifted (F2). One source of truth, not two implementations. |
| [`HabitRPG/habitica`](https://github.com/HabitRPG/habitica) | GPL-3.0, ideas only | Scoring lives in `website/common/script/` — **shared code the server executes**. The client never computes an authoritative number. Ours computes XP in the browser and posts it. |
| [`ppy/osu-web`](https://github.com/ppy/osu-web) | AGPL-3.0, ideas only | Ships explicit recalculation commands so a scoring change is *migrated* across existing users. We changed the curve with 8 users and no backfill — fine now, impossible at scale. |

The single structural lesson: **the level curve should exist once.** Today it
exists twice — JS and PL/pgSQL — and they have already diverged.

---

## Recommended order

1. **F1** — revoke the column grants. One statement, nothing legitimate breaks.
2. **F2** — make the server curve match, or stop computing `current_level`
   server-side at all and derive it from `total_xp` at read time.
3. **F3** — delete `DAILY_XP_CAP` or set it to the real ceiling; don't ship a
   constant that documents a policy nobody enforces.
4. **F4** — add `cardio_completed` to the `grant_action_xp` cap table.
5. **F5** — decide on pacing. Numbers above; happy to model alternatives.

F1 and F2 are defects. F5 is a product decision and I have not touched it.
